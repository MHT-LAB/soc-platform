# Security Design and Threat Model

The SOC holds keys that can isolate endpoints and reads sensitive telemetry, so it is itself a high-value target.

## Threats and controls
| Threat | Control |
|---|---|
| Prompt injection through alert fields (command lines, hostnames, file names, network text) | Fields passed as quoted untrusted data; read-only tool set; containment gate computed in code; injection fixtures in the test corpus |
| Compromised or over-privileged key | Per-client read-only key for triage; separate narrowly scoped key for response (isolate, rejoin, tag); keys held in a secrets manager and delivered as mode-600 files; never in repository, image, or notes |
| Public ingest endpoint abuse | One public route only; per-source secret or HMAC; rate limit; body cap; vendor IP allowlists where published; everything else reachable only over the mesh VPN |
| Server compromise | Non-root service user, minimal capabilities, read-only root filesystem where possible, key-only access over the mesh VPN, automatic security updates, default-deny firewall, no inbound port forwards |
| Cross-client leakage | Row-level client id, per-client keys and model sessions, per-client caps, cross-client correlation off by default |
| Silent failure of the SOC | Heartbeat detection, external uptime monitor, independent email channel, degraded banner |
| Runaway cost | Per-client and global caps that fail closed |
| Bad automatic action | Allowlist, stacked-evidence gate in code, would-have-done mode first, reversible actions only, one-tap rejoin, client authorization flags |
| Tampering with history | Append-only case log; signed reports are immutable and versioned |
| Client data handling | Contract language on AI-assisted analysis and retention; hash-only lookups for client files; per-client retention |

## Exposure rule
The only internet-facing surface is the ingest route behind a tunnel or reverse proxy. The console and API are reachable only over the mesh VPN.

**Database isolation (Sprint 1).** PostgreSQL runs in its own container on an internal compose network shared only with the public app, the pager worker and the one-off migration job. The tunnel is not on that network, and the `postgres` superuser is refused over the network. The only port published on the host is `127.0.0.1:5432`, for the console (a host-network service that reads cases as `soc_console`, a role with no table privileges whose only way in is four functions that return the raw payload as text and write only Ack and Close); it goes through a bridge that only the database joins and that has no outbound NAT, so no container can reach it and the database cannot route out. Residual risk: any process on the host (root, or the console itself if compromised) can try the loopback port; each role is limited by its own password and privileges. The public app connects as `soc_ingest`, a role with no table privileges whose only capability is calling `ingest_alert()`; the owner credentials exist only for the migration job. A compromised public app can therefore add alerts through that function and read nothing back. Residual risk: root on the host can read the database and every secret file, which is the same trust boundary as the rest of the host.

**Pager worker (Sprint 1).** A separate service turns alerts into cases and pushes them to a phone through a third-party push server. It is on the internal database network and on its own outbound-only network, and not on the tunnel's network; nothing listens and nothing is published. It logs in as `soc_worker`, a role with no table privileges whose only way in is nine functions that never return the raw payload and never accept a client id from the caller; a compromised worker can read pushes' worth of fields and mark pages sent or failed, and change nothing else. What crosses the push server is generic by design: client, rule name, host name, time and a short case id, built from sanitised fields (control characters stripped, lengths capped, plain text) and sent as JSON in the request body, never as HTTP headers, so alert text cannot inject a header or a second topic. The topic is the only secret in a push (on the public server anyone who knows it can read and post to it): it is generated on the host, stored mode 600 and in the secrets manager, never logged, never in a URL, never in an error code, and the client refuses redirects and any scheme but https. Floods are bounded: at most `SOC_PAGE_CAP` pushes per window, the rest wait and one notice says so. Residual risks: the egress network is not restricted to one domain (Docker cannot allowlist names; the host firewall is the open item); the push server sees the topic and the metadata above; a person who forges alerts through a stolen ingest key can buzz the phone up to the cap.

**Case pages on the console (Sprint 1).** The console now has two forms that change data (Acknowledge, Close). Because its only identity is a header that the tailnet proxy adds to every request from the person's browser, another website could make the browser send a post that carries it (cross-site request forgery). Every post therefore has to pass three independent checks, and any one failing writes nothing: the browser's own `Sec-Fetch-Site: same-origin`, an `Origin` equal to the console's own, and a per-person, per-case, per-action, per-day HMAC token made with a secret that only the console (and, later, the worker) holds. There is no script on any console page and the content policy allows forms to post to the console only. Alert text is attacker-written: all of it is HTML-escaped, control and bidirectional characters are made visible instead of obeyed, the raw payload is shown only as inert text, and a link becomes clickable only for the vendor's https console and only with URL characters. The console reads the database as `soc_console`, whose four functions never return structure from a payload and write only the Ack/Close state and one audit event each. Residual risks: the form secret and the database password sit in a root-only file on the host with the rest of the secrets; an analyst's own browser extension could still be abused to click the real buttons; Acknowledge by anyone on the allow-list is trusted (one shared role until sign-in arrives in Sprint 3).

**Acknowledge from a phone notification (Sprint 1).** The push can carry an Ack button whose link crosses the third-party push server. The link is an HMAC over one case and a 24-hour expiry with a key (`SOC_ACK_KEY`) held only by the worker and the console, never the form secret, with its own signing label; it is accepted only by a POST-only route that still requires the tailnet identity and the console allow-list, so someone who learns the push topic (and so the link) still needs a tailnet connection as an allowed person, and what they could do with it is acknowledge that one case within a day. A link preview or prefetch (a GET) never acts. A browser-marked cross-site request is refused. Urgent pages not acknowledged are sent again twice (15 and 60 minutes), which raises the number of pushes an attacker with a stolen ingest key could cause only up to the existing page cap.

**Console isolation (Sprint 1 hardening).** The console is a separate app and a separate service. The public app contains no console routes. The console service runs on the host network, bound to the host's loopback, so containers (including the tunnel) cannot connect to it; `tailscale serve` is the only path in, and it supplies the verified identity header. Residual risk: host networking gives the console container the host's network view (LAN and loopback services), so it stays non-root, read-only and capability-free, and holds only the console allowlist and the read-only EDR key. Any process on the host can also reach `127.0.0.1:8081` and send its own `Tailscale-User-Login`; only root-level host processes run on CT 110 today, so keep it that way.

## Failure of the human link
Page acknowledgement is tracked; high/critical alerts re-page every ten minutes, then email; an optional second commander removes the single-person bottleneck.

## Public export checklist
Before any note, diagram, rule pack or repository from this project is shared publicly, grep the actual diff (not only new files) and remove or generalize:
- Host, device and account names; usernames; filesystem paths.
- Network addresses, subnet layouts, tunnel and VPN identifiers.
- Tenant, organization, sensor and installation identifiers; URLs containing them.
- Client names, contacts, contract terms, and anything from client folders.
- Credentials of any kind, including disposable lab ones.
- Branding embedded in rule names, author email addresses in rule metadata.
- Pricing and rate cards.
- Anything that describes how the notes were produced rather than what the design is.
Treat every public technical write-up as reconnaissance material for someone profiling the author. If anything trips the checklist, stop and ask before publishing.
